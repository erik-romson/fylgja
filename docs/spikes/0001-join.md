## Method

For every registry row (A13 glob `^[0-9]+\.json$`; 14 rows today) the script walks the parent chain from the
session pid until a pid owns an AeroSpace window (`app-pid`). That pid's bundle id picks the host adapter:

- **cmux**: the window; plus the `CMUX_WORKSPACE_ID`, `CMUX_SURFACE_ID`, `CMUX_TAB_ID` and `CMUX_PANEL_ID` ids if
  the process args expose them (never the environment).
- **JetBrains**: among the opened projects of the newest product directory's `recentProjects.xml`, the project
  whose path contains the cwd (longest prefix wins); then the window whose title names that project. A title
  `<name> [<path>]` is an exact path match (confidence `high`); a plain `<name>` match is `medium`.
- **iTerm2**: title equals the session name, else the only window (best effort). No row used it today.
- **other**: the only window of the host app, else a shared workspace.

A row that cannot be joined prints `unresolved: <reason>`; so does a row whose pid is gone.

## Hit rates

Window hit means a single `window-id` was chosen. Workspace hit means an AeroSpace workspace was resolved.

| Host | Rows | Window hit | AeroSpace workspace hit | cmux workspace/surface id |
|---|---|---|---|---|
| cmux | 8 | 8 (100 %) | 8 (100 %) | 0 of 8 |
| JetBrains | 6 | 3 (50 %) | 3 (50 %) | n/a |
| iTerm2 | 0 | n/a | n/a | n/a |
| other | 0 | n/a | n/a | n/a |

- **cmux reaches 100 % for the AeroSpace workspace, but only at window level.** There is one cmux window for all
  8 sessions, so every cmux row gets the same window id and the same AeroSpace workspace, with `via`
  `chain+window` and confidence `window-only`. The exact cmux workspace and surface are not resolved for any row.
- **JetBrains misses the 100 % target: 3 of 6.** Rows 8, 9 and 14 are joined (rows 8 and 9 with `medium`, row 14
  with `high` via the `[<path>]` title). Rows 1, 10 and 11 are unresolved (below). Every one of the six has a
  project in `recentProjects.xml` whose path contains its cwd, so the project step works; the window step does not.

## Unresolved rows

| Row | Host | Reason printed | Why |
|---|---|---|---|
| row-1 | JetBrains (PyCharm) | `project is open but no window title matches it` | The cwd is exactly an opened project's path, but the IDE's project name is not the directory name, and `frameTitle` is empty for that entry. Windows of that app show titles of the form `<parent> <worktree-dir> – <file>`; two of them sit on one workspace, but the host app's 12 windows span several workspaces, so no workspace-only fallback applies. |
| row-10 | JetBrains (PyCharm) | `project is open but no window title matches it` | Same signature: the directory is named `main`, `frameTitle` is empty, and the windows with a `main`-like name show `<name> [~/<path>]` for other paths or a different name, so none equals the directory name or names this path. The IDE's project name for a `<parent>/main` layout is probably not `main` (check `.idea/.name`). |
| row-11 | JetBrains (PyCharm) | `project is open but no window title matches it` | Same as row-10: a different project whose directory is also `main`; no title names its path or equals its directory name. |

The IDE windows are open, but the data the join may use does not say which one belongs to the project. I did
not loosen the matching to hide this.
Two checks stayed deliberately strict: a plain name match is `medium` only, and a `[<path>]` title that names a
different path never matches.

One non-hit worth recording: before the `[<path>]` rule was added, a name-only match for `main` produced a wrong
`high` hit for row-14 (a different project named `main`). Name-only matching is therefore not safe as a
primary signal, and rows 8 and 9 (`medium`) are only as good as the uniqueness of their project names.

## What this means for A1

- **The parent-chain walk works.** All 14 chains end in a window owner, at most 5 pids long (`claude` → `zsh` →
  `login` → `cmux`; `claude` → `zsh` → IDE; and `claude` → `python3` → `uv` → `zsh` → IDE for norn-spawned
  sessions, which carry `entrypoint` `sdk-py`). No stale registry rows today.
- **Host mix today:** 8 cmux, 6 JetBrains (4 PyCharm, 2 IntelliJ), 0 iTerm2. R4's "most sessions are cmux" holds
  for the first host, but JetBrains is not a minor case.
- **cmux:** A1's first option ("process args or cwd expose the `CMUX_*` ids") does not work. No allowlisted
  name appears in any process's args. The `claude` args under cmux carry an inline MCP config with `CMUX_CUA_*`
  names including an auth token, so any arg-scraping must extract allowlisted names only and never store args.
  A1's other options stay open: the hook-time `CMUX_*` ids (A3) and the cmux CLI.
- **JetBrains:** the "project path contains the cwd" half of A1 is sound. The window half needs a second
  signal, because `recentProjects.xml` often has no `frameTitle` for an opened project and `displayName` lists
  modules. The title's `[<path>]` form is exact when it shows. Candidates for step 13 and WP1.8, to be tried
  and measured there, not here:
  1. read the project's own `.idea/.name` (the IDE project name), and match titles on it;
  2. use the hook-time envelope: `TERM_PROGRAM` and the JetBrains terminal's identifiers, if the hook can see
     any (A3 allowlist);
  3. fall back to the host's workspace only when all candidate windows share one (already done).
  Until one of these lands, the done criterion "workspace resolves for 100 % of JetBrains-hosted rows" is not met
  by the passive join alone. Run by hand to check option 1: `cat <project-dir>/.idea/.name` for the three
  unresolved rows' project directories.
- **iTerm2:** no rows; the rule is unexercised and stays best effort.

## What this means for step 04 (cmux spike, WP0.4)

Step 04 must answer, because the window-level join cannot:

1. Does the cmux CLI list workspaces and surfaces with a tty, pid or cwd, so that a session pid or cwd maps to a
   cmux workspace and surface? That would give exact cmux joins from outside any process's environment.
2. Is the cmux window title the selected cmux workspace or tab name? Today it is a single bare token of 7
   letters, with no separator, and the same for all 8 sessions. If it follows the selection, it is no join key.
3. Which `CMUX_*` names exist (`cmux --help`), and does the temp `--settings` file that cmux gives `claude`
   carry per-surface ids? It was not read here: run by hand `/Applications/cmux.app/Contents/Resources/bin/cmux --help`.
4. Whether focusing a cmux workspace also raises the right macOS window. With one window it is trivial, but
   the AeroSpace workspace is shared by all 8 sessions.

Fallback if step 04 finds nothing: cmux rows are reported at window level with confidence `window-only` and the
UI says so, as A1 already allows.

## Other findings

- `aerospace list-windows --json` needs `--format` for `app-pid`, `workspace` and the bundle id; with `--json`
  the format may hold only variables and spaces.
- `subscribe --all` sends four events on connect (`focus-changed`, `focused-monitor-changed`,
  `focused-workspace-changed`, `mode-changed`); the rest were not observed in a 5 s window (see the log).
- The script reads the registry with the A13 glob only, extracts allowlisted `CMUX_*` names from args in memory,
  never opens `*.key`, never reads another process's environment, and does not connect to any socket.
